# 自動要求検証とモデルdiff

2026-10-11のユーザー指示により、**自動要求検証とGitのようなdiff管理を必須能力**とする。[競合調査](competitor_tradeoff.md)の旧採用判定は根拠にしない。以下の詳細な受入条件は設計草案であり、実装済み機能や採用baselineではない。正式なプロジェクト要求は、レビュー後に版付きJSONの正本へ記録する。この検討文書を独立した要求ストアにしない。英語の詳細版は[こちら](../en/verification_and_diff.md)。

## 自動要求検証

`構成変更 → 影響する検証ケース → 予算内の実行 → 決定論的判定 → 証拠の記録 → 要求への適用確認`

One-Pieceは要求・試験・評価条件・構成・証拠の正本を管理する。Engineering Agentsは登録済みのMuJoCoなどの実行アダプタを呼ぶ。要求IDやLLMが書いた文章だけから実行コマンドを決めない。要求標準の第一参照はISO/IEC/IEEE 29148:2018とし、NASA標準・要求記述ガイド、ASD-STE100の順に適用する。

受入条件の草案:

- 結果に要求、試験、モデル、制御器、評価条件の版と、入力digest・評価器の版を固定する。
- 数値・単位・閾値・時間・必要条件を評価器で判定し、LLMの説明で結果を上書きしない。
- 合格、不合格、未実行、判定不能、実行エラーを区別する。GPU未実行や証拠不足を合格にしない。
- 6秒の数値試験を実機30秒保持の合格へ読み替えない。数値整合と実世界の妥当性確認を区別する。
- 要求・閾値・モデル・制御・評価器が変わったら、旧結果の適用可否を再確認する。旧結果と版参照は保存する。
- 人間とエージェントに同じ記録から要求別の条件網羅と未検証事項を示す。証拠の取込と人間のbaseline確定を区別する。

最小の確認は、合格、不合格、入力欠落、閾値変更の4ケースとする。閾値変更後に旧要求の合格を自動流用しないことを示す。物理入力が変わった場合はシミュレーションを再実行する。閾値だけの変更は、保存済み測定値の条件網羅と出自が十分なら再評価できる。その判断と理由を記録する。

## Gitのような変更管理と意味を持つdiff

Gitで正本の履歴を保持し、その上にモデルの意味を比較するdiffを設ける。

受入条件の草案:

- 変更前後の構成をID・revision・内容ハッシュのmanifestで固定する。Git commit、モデル構成、SysML APIの公開Commitを混同しない。
- 要求、KDP、詳細パラメータ、評価条件、グラフ関係、成果物参照の追加・削除・変更を示す。
- 変更箇所のJSON path、旧値、新値、単位、承認状態、参照先の版を保持する。未設定とnullも区別する。
- グラフの向きと端点の版を比較する。順序だけの違いと意味の変化を分けるが、意味を持つ配列の順序は失わない。
- 同じdiffデータをLLM向けJSONと人間向けHTMLに出し、元の構成をたどれるようにする。
- 影響する要求・試験を列挙する。影響解析できない部分は明示する。差分だけで因果や要求合格を断定しない。
- 要求や評価条件の競合は明示した判断で解決する。同一revisionを上書きしたり、閾値を黙って選んだりしない。

最小の確認では、パラメータ値、単位、要求の閾値、関係の端点revisionを変え、記録の追加・削除も含める。すべての変更が見え、同じ比較を再実行しても結果が一致し、比較基準の正本が変わらないことを示す。

## 現在の実装範囲

**One-Pieceにあるもの:** 不変の版付き記録、原子的取込、参照・成果物検査、Git上の正本、同じ記録を読むcontext／HTML、HTML上の限定的な設計パラメータ比較。`onepiece check`は記録の整合性と証拠の主張範囲を検査する。シミュレーション実行や全要求への適合判定ではない。SysML APIの`diffCommits`は未実装である。

**Engineering Agentsにあるもの:** Cube専用アダプタによる予算内のCPU実行、GPUが利用できる場合の確認、保存した数値screening条件の評価、開発試験ケースへつながる結果。汎用の要求検証スケジューラではない。

**これから必要なもの:** 汎用の検証計画・実行契約、要求別の条件網羅と証拠の適用可否、構成のsemantic diff API／CLI、JSON／HTML共通のdiff表示、変更に応じた再実行。branch／merge時の競合解決やSysMLの標準diff操作も、別途実装と試験が必要である。

次のMVPは既存Cubeでこの流れをつなぐ。自動変更の許可範囲、制御周期、固定刻み、CPU／GPU確認方針を維持し、半刻み確認は加えない。まず「変更→diff→影響試験→再実行または根拠付き再評価→証拠→条件網羅の更新」を最小ケースで示す。
