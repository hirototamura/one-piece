SYSTEM MODEL CONNECTION GRAPH

Follow relationships from any object

Select an object to see its directly connected objects and the relationship labels between them. The graph includes hierarchy, allocation, design constraints and verification; use the edge filters to control density.

Each vertex is a versioned model object. Select it to inspect key attributes and incident relationships; expand “All source attributes” for its complete record. The current focus stays on the left and connected objects appear on the right. An outgoing arrow points right (focus → connected object); an incoming arrow points left (connected object → focus). Read the relationship sentence in the inspector to see both endpoints. Double-click or choose “Center graph” to follow one hop at a time.

RELATIONSHIP SEMANTICS
  • derivesSource requirement or requirement set → derives → derived requirement or requirement set.
  • satisfiesDesign or product → satisfies → intended requirement; correspondence is not proof of a pass
  • verifiesTest case or evidence → verifies → requirement
  • allocatesRequirement → allocates → function; function → allocates → component. Shared installation and sourcing requirements can allocate directly to several components.
  • performsCube or external verification context → performs → function
  • comprisesCube or external verification context → comprises → component; physical decomposition is separate from requirement derivation
  • constrainsRequirement → constrains → design parameter

Direction and coverage: graph arrows follow subject → verb → object, independently of hierarchy. For requirement-to-requirement derivation, SysML `«deriveReqt»` has the opposite notation direction (derived/client → source/supplier), which is mapped here to the readable sentence source → derives → derived. Recorded `derive` links are shown as `derives`, including links through requirement sets. Membership and parent fields support breadcrumb navigation; they do not replace recorded derivation links. Verification method is stored as an attribute on each verification case. Product records describe system or subsystem concepts, not a complete parts list.

IDENTIFIERS & HIERARCHY

Record IDs and graph levels answer different questions

In this project, letter prefixes are naming conventions for record families. The fields on each record define its exact role; a prefix alone does not say whether it is a group or an atomic obligation.

M-MissionM-VERTEX states the top-level mission.
R-RequirementR-HOLD and R-DRIFT are measurable obligations. R-DRIVE is a group record.
C-Constraint-style obligationC-BUDGET and C-FIT-PRINT are obligations. C-FIT is their organizing group.
D-Design parameterD-CORNER-R is a design value with provenance and units.
I-Identification parameterI-MU is a value to identify; its provenance can say assumed or unknown.

cube.system-model.active is a separate, dot-namespaced record ID with kind system_model. Its simulation_snapshot_ref points to a specific versioned snapshot. Dots and letter prefixes do not create graph levels: grouping uses explicit membership and parent_ref; requirement derivation uses «deriveReqt». This prefix convention is project-specific, not a universal schema enum.

STATUS LABELS

Read each label on its own axis

Several labels can apply to one requirement at the same time. They describe different things, not steps in a single status ladder.

Requirement · statusREVIEWED

The current wording was reviewed by a person. New proposals start as draft; the earlier wording state is preserved separately as source_status.

Human decision · approval_stateHUMAN REVIEWED

The human accepted this requirement and allocation scope. New proposals can use pending_human_review. This is separate from whether an item has been tested.

Verification · verification_statusNOT RUN

The requirement's check has no recorded execution. Its linked case can separately say status: planned and execution_status: not_run.

Physical evidence · physical_verifiedNOT PHYSICALLY VERIFIED

This display is derived from the field, which is null or false for the current records. It is not a separate stored status string.

Parameter provenance · originASSUMED / UNKNOWN

For D- and I-parameter records, this describes where a value came from. The current linked set includes assumptions and values whose origin is unknown.

Work still needed · hardware_verification_requiredHARDWARE CHECK REQUIRED

A boolean planning flag, not a pass/fail result. Simulation evidence alone does not clear a required physical check.

Vocabulary status: these are the values and display labels currently present in the model. The record schema does not define a complete allowed-value list or transition policy. Agree that policy before introducing new official labels.

REVIEW WORKFLOW

How to review and update a draft

Use the site to prepare and discuss a change. Canonical records remain in One-Piece and are versioned.

  1. Read the exact item and revision.Confirm its parent, owner/product, rationale, conditions and source lineage. A group node is only a container; review its child obligations.
  2. Check that the statement is clear and testable.Keep one obligation per sentence. Resolve vague terms, define units and bounds, and make the acceptance rule measurable.
  3. Check how it will be verified.Review the method, planned case, test conditions, evidence needed and unresolved items. A planned case is not a result.
  4. Record a proposal here.Edit the wording, add the reason or question, and optionally propose a label field/value. Save locally, then use Export review to bring the packet into our conversation.
  5. Change official labels only with the matching basis.Update wording/review fields after human review; update verification fields only when a result is recorded; set physical verification only from applicable hardware evidence.
  6. Append a new canonical revision.Do not overwrite history. Preserve the source status and provenance, update references that should point to the new revision, validate the One-Piece records, then rebuild this projection.
What this site can change: browser-local wording and label proposals only. Saving or exporting a proposal does not change an official status, approve a requirement, or create verification evidence.
TRACE RELATIONSHIPS

What each graph edge means

Read directed edges in sentence order: subject → verb → object. The verb label is shown in active form.

derivessource requirement or requirement set → derives → derived requirement or requirement set
allocatesrequirement → allocates → function → allocates → component; some shared obligations allocate to several components
constrainsrequirement → constrains → design parameter
satisfiesdesign → satisfies → intended requirement; correspondence only
verifiestest case or evidence → verifies → requirement; carries method, outcome and applicability

A trace edge never upgrades a draft to approved or an unrun plan to a pass.
